# Codia 功能增强与新增方案

日期：2026-10-16\
基线：main `f668ee05b91ed54b65d62aa791446083e12bb643`\
范围：产品规划，不包含本轮代码修改或发布。

## 一、建议的产品方向

把 Codia 从“功能丰富的 AI 桌面工作台”，提升为“能交付结果、能解释过程、出错能恢复的个人与小团队 Agent 工作台”。

现阶段不建议继续堆叠聊天入口、Agent 数量或设置页。先让用户明确回答四个问题：正在做什么？需要我决定什么？结果在哪里？失败后能否接着做？

这里的“行业最佳实践”指官方工程文档支持的方法，不代表存在适用于所有产品的唯一标准。以下路线是结合 Codia 代码推导的建议。

## 二、已有能力：应增强，不能重复建设

最新源码已经包含：

- 聊天、多 Agent 频道、子任务、任务依赖及验收标准。
- 可视化工作流，以及脚本工作流的并发、流水线、结构化输出、token 预算和 journal replay。
- 定时自动化、执行记录、超时及中止。
- 多供应商与本地模型、按角色路由、用量账本。
- 长期事实记忆、摘要、固定记忆、标签和全文检索。
- MCP HTTP/stdio、OAuth、刷新重连、Agent 级授权。
- 审批网关、沙箱、审计与执行租约。
- Live2D 运行时与资源加载。

注意：有源码不等于完整用户旅程已验收。此前工程测试通过，但真实模型的多 Agent 交付、实际工作流和云端全天候运行仍需专门验证。云环境 WebGL 限制也不能据此推断普通用户设备不能显示 Live2D。

## 三、现有功能增强

### P0-1：工作流状态必须可信

**当前证据**：画布在 assign/trigger 请求成功后即把节点标为 succeeded；请求派发成功不能等同于实际任务完成。脚本 parallel/pipeline 捕获分支异常返回 null 时，整体仍可能显示 done。这是静态代码发现，需先复现，不能当作已完成运行验证。

**设计**：

- 统一 Run ID、Step ID、产物引用与状态事件，连接画布、团队任务及脚本执行。
- 区分排队、执行、等待审批、部分失败、取消、真正成功。
- UI 根据后端真实终态展示结果；派发成功只进入“已排队”。
- 每个失败节点显示原因、已完成产物及“仅重试失败步骤”。
- 提供 fail-fast / collect-errors 等明确策略，不静默吞掉异常。

**验收**：真实模型执行“检索→起草→审核→修订→保存”，任一节点失败不得显示全绿；取消后不得继续派发后续节点。状态需与执行事件逐项对应。

**工作量估计**：8–12 人日，取决于现有事件模型能否复用。

### P0-2：可恢复执行与副作用防重复

已有手动 replay，但重启遗留 running 当前会被判 failed。应补足恢复策略，而非重写所有引擎。

- 建立持久动作账本与稳定 action ID，记录计划、执行中、确认成功和结果未知。
- 区分安全重试的读操作与可能产生重复副作用的写操作。
- 崩溃后展示“恢复、检查外部结果、取消”，不盲目重放发送、上传或提交。
- 固定运行使用的流程、工具及提示词版本，避免恢复时行为悄然变化。

**验收**：强制结束进程后能定位最后确认步骤；模拟“外部写入成功但客户端超时”，不得直接重复写入。不支持幂等的外部服务不承诺 exactly-once。

**工作量估计**：10–15 人日。先覆盖文件写入和一种外部写操作，再扩展。

### P0-3：现有审批与安全能力统一呈现

已有审批网关、沙箱和 MCP 授权，重点是串联和验证，不再增加另一套权限系统。

- 审批卡显示动作、目标、参数变化、权限范围、有效期及预期副作用。
- 批准绑定动作和参数摘要；参数发生实质变化时重新判断。
- 文件系统与网络边界同时生效，MCP 子进程继承限制。
- 连接器展示来源、版本、授权范围、最近使用与健康状态。
- 回归验证 OAuth audience、重定向和元数据地址校验、敏感信息脱敏；这里是待验证清单，并非已确认漏洞。

**验收**：审批重启后可找回；拒绝动作不能通过换工具执行；过期批准不可复用；测试凭据不进入聊天及可导出日志。

**工作量估计**：6–10 人日，不含重建底层沙箱。

### P1-1：团队从“分工聊天”升级为“可验收交付”

- 每个任务有负责人、输入、交付物格式和验收条件。
- 独立研究可并行，共享文件修改采用明确的写入责任人及冲突检测。
- 子 Agent 返回产物、依据、未解决问题，而非只返回“已完成”。
- 默认单 Agent；仅在独立子任务可并行且实测有收益时启用团队。

**验收**：同一任务集比较单 Agent 与多 Agent 的成功率、耗时和成功任务平均成本。多 Agent 无收益时允许回退。

**工作量估计**：6–10 人日，依赖统一运行模型。

### P1-2：自动化成为可靠调度

源码已有 cron，但逐任务 await 可能使长任务拖延其他任务；未见逐任务 IANA 时区。

- 引入任务级时区、DST 行为说明、漏跑策略（跳过/补一次）与并发上限。
- 调度与执行分离，失败退避与去重键独立配置。
- 通知分为完成、失败、待审批；默认不为每个中间步骤打扰用户。
- 桌面休眠时明确显示不可保证执行，不把本地定时器包装为全天候云服务。

**验收**：一个长任务不阻塞其他到期任务；跨时区、重启、重复触发和补跑均有测试。

**工作量估计**：6–9 人日。

### P1-3：模型诊断与成本控制

复用角色路由和用量账本，增加“这个模型是否能完成我的任务”的体检。

- 分别检测文本、工具调用、视觉、结构化输出等能力。
- 显示供应商不兼容项，提供针对性的配置建议。
- 每个 Run 有费用、步数、时长预算，触顶后安全暂停。
- 轻任务优先低成本模型/确定性代码，复杂任务按评测结果升级。
- 区分供应商实际账单与本地估算，未知价格不能记作免费。

**验收**：模型切换通过固定质量集；受控超支边界可测；以“成功任务平均成本”衡量优化。

**工作量估计**：5–8 人日。

### P1-4：记忆可追溯、可纠错

现有事实库具有来源字段基础，但常规插入路径未完整写入来源。

- 每条记忆显示来源会话/文档、更新时间及作用范围。
- 支持用户纠错、冲突提示、过期标记和删除。
- 先完善来源与隔离，再扩展语义检索；不要把现有全文检索宣传为完整知识库。

**验收**：记忆能跳回证据；删除后不再检索到；项目 A 的私有资料不进入项目 B。

**工作量估计**：5–8 人日。

### P1-5：前端聚焦任务，而不是按钮

- 首页以“继续任务、待我审批、最近产物”为主要入口。
- 把运行、重跑、恢复放入同一上下文动作区，避免同时出现含义冲突的主按钮。
- 简单模式显示目标、输入和结果；高级参数渐进展开。
- Live2D 保持正常动态显示，可由用户手动关闭或降低动态效果。初始化、加载或绘制失败时显示明确错误与重试入口，不自动替换为静态形象；不阻塞核心功能。（2026-10-16 用户修订）

**验收**：新用户无需解释即可完成首个模板任务；键盘能完成主路径；无 WebGL 时聊天与任务照常可用。初始化、加载与绘制失败均不切换静态形象；重试须重新初始化，成功后恢复动态显示。

**工作量估计**：4–7 人日，可与后端并行。

## 四、值得新增的产品能力

### 1. 任务控制台与成果中心（优先）

把现有分散记录组合为新体验，而非新增一套执行引擎。

一个页面回答：谁在执行、卡在哪里、花费多少、等待什么、交付物在哪里。成果支持版本、来源、预览、导出和对比；已有能力优先复用。

最小版本：统一任务列表＋运行详情＋产物引用＋待审批入口。估计 7–10 人日，依赖 P0 状态模型。

### 2. 任务模板库＋执行前预检（优先）

不是先建开放市场。先交付 3–5 个经过评测的官方模板，每个模板说明输入、工具权限、预计耗时/成本、输出与失败处理。

预检检查模型能力、MCP 连接、目录权限和预算。模板用不可变版本，更新不能悄悄替换正在运行的任务。

最小版本估计 5–8 人日。发布门槛是模板真实运行通过，而非只有漂亮示例。

### 3. 评测与运行诊断工作台（优先给开发者）

把模型调用、工具、审批、重试与产物关联到 trace ID。支持脱敏导出、失败案例回放，以及模型/提示词/模板版本比较。展示事件和可验证摘要，不要求暴露模型隐藏推理。

首批建立 30 个有标准答案或评分规则的真实任务，覆盖成功、失败、安全和恢复场景。新增确定性关键安全/恢复用例必须全部通过；模型任务先测基线再定提升目标，不凭空承诺成功率。

估计 7–12 人日，可先作为内部发布门禁。

### 4. 带引用的项目资料空间（第二阶段）

扩展现有记忆为文档资料管理：导入、增量索引、出处定位、版本和删除传播；初版限定少量格式及单项目。

与“记住用户偏好”分开：文档事实有来源，偏好可以纠错。多用户共享、细粒度权限和超大规模索引后置。

估计 10–15 人日，依赖来源/权限模型。

### 5. 可离线继续的远程执行（后置）

明确区分两种产品：连接用户自有服务器；提供托管执行环境。建议先做自托管远程 worker，再评估托管云服务。

需持久队列、租约/心跳、版本兼容、断线重连、密钥边界、配额和费用上限。桌面关闭后任务由远端继续，重连显示真实状态；桌面专属工具不能伪装成云端可用。

估计自托管 MVP 15–25 人日；托管版涉及运维、安全、成本与服务承诺，另行评估，不纳入首期交付。

## 五、建议实施顺序与投入

估算假设：2 名熟悉项目的全职工程师，兼职产品/测试支持。人日是粗估而非承诺，各项有复用与并行，不能简单相加当作交付日期。先用 3–5 个工作日做状态链路、运行模型与测试基线的技术勘察，再校准。

| 阶段      | 目标     | 首选范围                    | 出门标准              |
| ------- | ------ | ----------------------- | ----------------- |
| 第 1–2 周 | 结果可信   | 真实状态、错误语义、首条真实模型旅程、运行ID | 不再派发即成功；失败可定位     |
| 第 3–4 周 | 中断可处理  | 持久动作账本、审批关联、恢复、防重复      | 重启/超时/取消/重复触发用例通过 |
| 第 5–6 周 | 用户能交付  | 任务/成果中心、模型预检、3个模板       | 真实任务可走通，用户能找到产物   |
| 第 7–8 周 | 可测量地改善 | 评测门禁、预算、重点自动化与前端调整      | 可对比质量/成本/耗时，回归可发现 |
| 后续      | 扩展范围   | 来源记忆、项目资料、自托管远程worker   | 隔离/恢复/运维验收后再开放    |

八周目标是纵向 MVP，不是上述全部功能完整上线。若只有一名工程师，应优先保留前三阶段核心路径并顺延扩展项。

## 六、首批三个实战模板

### A. 行业研究简报

用户输入主题、范围与截止时间 → 检索并保存来源 → 提炼结论 → 审核引用 → 导出简报。\
验收：引用可打开且支持结论；区分事实和推断；无证据明确说明；超过预算暂停。

### B. 仓库检查与修复候选

选择项目 → 运行现有检查 → 定位失败 → 生成最小补丁 → 重跑针对性测试 → 展示 diff 与报告。\
验收：工具限于项目范围；不自动推送主分支；报告区分本轮引入与既有问题；发布动作需明确授权。

### C. 定时周报

选择资料源和模板 → 定时读取 → 汇总变化及待办 → 形成草稿 → 用户审核后发送。\
验收：时区明确；漏跑有记录；相同周期不重复发送；引用原始资料；未授权不发送。

## 七、不建议现在优先做

- 开放插件市场、Agent 商店：先把权限与版本治理做好。
- 更多重复聊天/团队入口：先统一任务与产物模型。
- 默认多 Agent 跑一切：可能增加成本和协调失败。
- 承诺任意平台完全自动 Computer Use：能力与授权边界必须清晰。
- 先做 Live2D 情绪、语音口型或复杂装饰，再补可靠性：保留特色，但不能掩盖任务失败。
- 一次性接入所有云平台：先证明一种远程执行链路可靠。
