# 自动化运行健康与安全试跑

实施日期：2026-10-19（UTC）。工作目录：`/workspace/shared/codia-memory-implementation`。

## 已完成

- 自动化计划展开后显示运行健康、连续失败次数、后续周期最早执行时间、最近 20 条运行历史。
- 区分成功、执行超时、错过周期并跳过、一次性失败、普通失败、正在执行，以及服务中断后已领取但未确认结果的未知状态。停用不再被解释为成功。
- 新运行保留原活动 ID 与原会话引用；成功和失败都可关联。有活动记录时通过现有只读会话接口预览，不提升活动、不改动原聊天；老记录缺引用时明确显示不可用。
- 每 15 秒刷新计划及已展开的健康面板；手动刷新计划会同步刷新展开的历史。历史和模型列表分别提供局部重试，失败显示错误并保留上次成功数据，不冒充空列表。
- 同一个任务的未保存字段不因对象替换、自动刷新或另一个任务保存而丢失。未保存时不能试跑，防止误以为运行了新草稿。
- 试跑接入既有调度器，先落盘幂等收据，再派发执行。快速重复点击、同一 requestId 的并发/重复请求、完成后重发或服务重启后重发，都只返回已有收据。
- 断网、服务重启或结果落盘失败后，不自动重发 POST。未知结果、超时或失败需要先核对已有结果与外部影响，显式确认新运行；后端核对当前 reviewKey，过期确认不能放行。
- 原有模型、工作目录、时区、并发限制、权限和审批路径保留。运行中的调度器仍占用并发槽；超时并不表示外部动作回滚。
- 同毫秒的后台活动增加唯一 ID，避免并发任务的原结果引用碰撞。

## 使用

1. 打开“自动化”，选择助手，展开一个计划。
2. “运行健康”显示当前状态与历史；“刷新运行记录”仅重试该计划的读取。
3. 点击一条记录的“查看原结果会话”，可在面板内只读查看已有活动文本。原文件缺失或无权读取时显示错误，可以原地重试。
4. 编辑后先保存，再点击“试跑一次”。阅读真实执行提示后点“确认试跑一次”；取消不会派发。
5. 如果上次失败、超时或结果未知，先核对原会话及外部服务，再勾选“已核对上次结果与外部影响，仍要新运行一次”。这是一次新的运行，不是重放旧请求。

“试跑”是真实执行入口，可能产生模型费用或外部动作，不是沙箱 dry-run。运行仍须经过现有审批；本次实现与验证未调用真实模型、未执行外部动作。

## API 和数据边界

- `GET /api/desk/cron/:id/health`：只读健康与最近历史；保留现有本地所有者访问边界。
- `POST /api/desk/cron`、`action: "run-now"`：现在必须带 `id` 和稳定的 `requestId`（8–128 位字母、数字、点、下划线、冒号或短横线）。首次接受返回 202 和持久收据；重复 requestId 返回 200 与原收据。客户端应通过 GET 查结果，不能因 POST 超时生成新 ID 自动重发。
- 当 `requiresReview` 为真时，新运行必须带用户核对后的当前 `reviewedRunKey`；已在执行或确认过期返回 409。试跑使用保存的任务所属助手，不跟随当前聊天焦点误派发。
- 手动收据与计划保存在同一原子写入的 JSON 文件中，不自动过期，避免旧请求在历史裁剪后重新执行。原 JSONL 运行历史仍使用既有保留策略：超过 500 条时裁剪到最近 300 条；界面显示最近 20 条，不声称完整审计账本。
- 异步手动收据绑定发起时的 Studio 存储实例，完成时不会因用户切换 Studio 写入另一处。
- 这是既有单进程本地调度器的幂等保证，不是分布式锁，也不是对外部系统“恰好一次”事务保证。旧文件手工回滚、删除记录或多进程同时写入不在保证范围。
- 周期性计划仍按原时区与错过周期策略执行下一周期；本轮没有自动重放失败的那个周期，也没有修改原计划策略。真实试跑仍按原调度器规则更新下次运行时间、退避和一次性停用状态。
- 旧记录没有原会话引用时，不从其他聊天猜测或拼接证据。超时发生在会话返回前，也可能暂无可打开引用。
